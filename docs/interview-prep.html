Part A: understand the project

1. One-minute pitch

Problem. Students juggle classes, labs and many deadlines, and their plan breaks the moment one study session doesn't happen. Re-planning by hand is tedious, so they stop planning.

Who it's for. Students like me at IISc, whose assignments live in Microsoft Teams. Visitors and recruiters can try a realistic demo week with no sign-up.

What it does. You add classes, deadlines and preferences. An optimizer (Google OR-Tools CP-SAT) places 30-minute study blocks so that every deadline is met, demanding work lands in your focus hours, and big tasks are split into chunks. Mark a block "not done" and the rest of the week is replanned at once. If the work can't all fit, it says exactly how many hours don't fit and offers checked fixes: extend one deadline, or cut hours.

What stands out.

  • A real optimizer, benchmarked against a greedy earliest-deadline-first baseline on 90 generated workloads. It met 1725 deadlines vs 1674, with 782 h of lateness vs 1165 h and 3089 preference violations vs 4479.
  • Teams import from a screenshot. You press Windows+Shift+S then Ctrl+V; Gemini reads it, with Tesseract OCR as the fallback; you review everything before it's saved.
  • Built spec-first: 68 requirements and 48 pass/fail acceptance criteria, with every change logged.
  • Free to run, no login, and private 256-bit planner links.

2. Architecture and request flow

Flow 1: marking a block "Not done"

  1. Route. streamlit_app.main() sees ?p=<id>. planner_route() checks the ID against ^[A-Za-z0-9_-]{43}$ and that it exists, then renders planner_page() with PlannerService(SupabaseRepo, id).
  2. Click. The FullCalendar component returns eventClick. calendar_view.apply_click() selects the block once (repeat reruns are ignored) and asks the page to scroll to the highlighted panel.
  3. Handler. "Not done" calls run_action(service.mark_not_done), which shows a spinner and turns any error into a plain message.
  4. Module. PlannerService.change() applies the pure state change planner.mark_not_done() (the block's unfinished minutes return to its task), refreshes overdue tasks, then _commit():
    • build_problem() builds the 30-minute grid from now;
    • make_plan() solves strict CP-SAT, starting from a hint plan. If that is proven infeasible it runs diagnose(); if time runs out it uses the greedy plan;
    • validate() checks the result with the rule set for its plan type.
  5. Database. storage.save_changes() writes the difference: new and changed rows first, then deletions, and the plan metadata (including the input hash) last. If any write fails, the next load notices the stale hash and replans.
  6. Response. The page reruns. The calendar gets a new key (calendar-<plan_version>) and shows the new plan.

Flow 2: pasting a Teams screenshot

  1. Browser. The paste box (ui/clipboard_paste.py, a Streamlit components-v2 widget) is contenteditable, so Ctrl+V fires a real paste event without any clipboard permission. The JavaScript reads the image, checks its type and size, and sends it once as a data URL.
  2. Handler. import_view.pasted_screenshot() → read_pasted() → decode_pasted(), which accepts only PNG, JPEG or WebP, valid base64, and ≤ 10 MB, and checks it really is an image. Then the same _read() runs as for uploads.
  3. Service. pipeline.import_screenshots() first tries Gemini: inline image bytes, a fixed JSON schema, and the due text copied verbatim. If there's no key, an error, a timeout, bad JSON or zero rows, it falls back to Tesseract and the rule-based parser. dates.resolve_due() turns "Due tomorrow at 11:59 PM" into an IST deadline, with a flag.
  4. Response. An editable review table: problem rows first, and completed, duplicate or past rows unticked. Nothing is saved until "Add selected tasks", which goes through service.change() and replans. The image is never stored.

4. Data model and the key algorithms

Tables (db/schema.sql)

  • planners: id (43-character token), prefs jsonb (the plan metadata lives in prefs._meta)
  • events: class, lab, other or blocked; one-off or weekly
  • tasks: type, raw and used estimate, deadline, demanding, status, actual hours, learning_eligible
  • blocks: start, end, status (planned, done, not_done or skipped), actual minutes, plan version
  • import_log: Gemini and Tesseract calls, for the daily limit

Every table has row-level security enabled and no anon policies. Everything belonging to a planner is deleted with it (ON DELETE CASCADE).

Scheduling model (solver.py)

  • Grid: 30-minute slots from now (rounded up) to midnight at the end of the horizon (default 7 days, max 14), in IST.
  • Hard rules: only free slots; one task per slot; all work before its deadline; runs ≤ the max block; blocks ≥ min(min block, the work); the daily cap, counting work already done today.
  • Goals, in order: demanding work in focus windows, then fewer blocks, then earlier days (then stability, on a replan).
  • Modes: strict, minimum shortfall (diagnosis), minimum lateness (benchmark).

Worked example: "can't fit everything" (from tests/test_diagnose.py)

It's Wed 14 Oct, 10:00, with the default preferences (day 08:00–23:00, max 8 h of work per day). Task A needs 6 h by 18:00 today and task B needs 5 h by 23:00 today. That's 11 h of work, but today allows only 8 h.

  1. Strict CP-SAT is proven infeasible.
  2. The minimum-shortfall model gives H = 3.0 h that can't be placed. One optimal split is A 2 h and B 1 h.
  3. Cut option: remove exactly that shortfall, re-solve strictly, and confirm it fits before it's shown.
  4. Extend options: for each task, relax only its deadline and minimise its finish time. Both come out as Thu 15 Oct 11:30, because tomorrow from 08:00 the remaining 3 h needs a short gap after a 2-hour run. Each option is then re-solved to confirm it.
  5. The UI shows "3 h don't fit" with an Apply button for each option. Applying one replans the week.

Pro-rata share (R17, D-16)

A task due after the horizon gets ⌈remaining × horizon ÷ time to deadline⌉ slots, due at the horizon end. In the test, 10 h due in 14 days with a 7-day plan from Wed 10:00 gives exactly 5 h this week.

Learning (R37, R38)

factor = 1 + n/(n+2) × (r − 1), clamped to [0.5, 2.5], over the last 10 confirmed tasks of a type. Three lab reports estimated at 2 h that took 3 h give r = 1.5 and factor = 1.3, so a new 2 h estimate becomes 2.6, rounded to 2.5 h.

6. Spec-driven development

  • SPEC.md came first, with no code. It has 68 requirements in EARS form ("WHEN … THE SYSTEM SHALL …"), 48 pass/fail acceptance criteria, Must/Should priorities, 23 recorded decisions and a changelog (v0.1 → v0.12).
  • PLAN.md maps every task to its R# and AC# across 10 phases. Phase 1 was a live deployment check (Supabase write and read, plus one Gemini call) before any feature code. It has a traceability table with each AC's status.
  • Feature commits cite Refs: R#, AC-#. Every spec change was committed separately as docs(spec), almost always before the code that relied on it. The exception: R16's v0.6 change was logged right after the commit that introduced it.

Spec changes and why

  • v0.5, AC-3: the secret scan matched key names written in SPEC.md itself, so it could never pass. It now matches only real key formats (e.g. sb_secret_ + 20 characters).
  • v0.6 / v0.7, R16 (D-21): a single weighted objective couldn't be proven optimal within 10 s, which broke the speed criteria. The goals are now solved one after another, each with a time cap.
  • v0.8, D-23: in the benchmark's lateness mode, the optimizer kept the min-block rule while greedy ignored it, so the optimizer lost on lateness (1281 h vs 1165 h). The rule became a soft goal in that mode, consistent with D-12. Result: 782 h vs 1165 h.
  • v0.10 / v0.11: live testing found that the demo's past blocks were hidden behind "‹", so the calendar now opens 2 days back. New R68 added screenshot paste with Ctrl+V.

7. Testing, CI and deployment

  • 174 tests (pytest), covering: solver rules, the validator, diagnosis (exact H, verified options, the budget on a fake clock), learning, the date-resolver table, the parsers, the import pipeline, export, storage contracts, demo invariants and Streamlit AppTest UI flows.
  • No network, no secrets: pytest-socket allows only localhost; Gemini is a fake client; storage is MemoryRepo. Synthetic Teams screenshots carry a marker chunk, and a test fails if a committed image lacks it. Real screenshots live only in the git-ignored private/ folder.
  • Benchmark as a test: python -m bench.run_benchmark --seeds 10 checks AC-5 and AC-20 to AC-23. There were 0 validation failures, and the 20-task median was 1.51 s (p95 4.72 s).
  • CI: GitHub Actions on ubuntu-24.04, Python 3.13, with Tesseract installed, running plain pytest. Keep-alive: a cron job every third day pings Supabase, cleaning the secrets first and printing only the HTTP status.
  • Deployment: Streamlit Community Cloud from main (Python 3.13); packages.txt installs Tesseract. Secrets go only in the Cloud secrets box, .streamlit/secrets.toml (git-ignored) and GitHub encrypted secrets. A log scrubber removes keys and planner IDs from logs, and a test scans tracked files for real key formats.
  • Live checks (owner, 16 Oct): the demo, click-to-scroll, done and not done, overload, and a Brave clipboard paste that read a real Teams page correctly. AC-17 (3 real screenshots) and AC-40 (the anon-key test against the real database) haven't been run yet.

8. Real problems and how they were fixed

1. The solver couldn't prove optimality in time

One weighted objective made demo weeks hit the 10 s limit, which broke the speed targets. Profiling showed each goal alone proved in about a second, but not all three together. Fix: solve the goals one after another, with per-goal time caps once a plan exists. The demo median went from timing out at 10 s to about 0.85 s.

2. The starting hint made plans worse, and one setting crashed OR-Tools

The greedy hint broke the min-block rule, so CP-SAT discarded it; one overloaded case came out at 733 h of lateness. Turning on repair_hint crashed the whole process (an OR-Tools 9.15 check failure with several workers). Fix: removed repair_hint; added hint_plan(), which places EDF work in whole runs that respect the block rules; and hinted every variable, not only the slots. The benchmark then passed every check.

3. CI failed before any test ran

ModuleNotFoundError: No module named 'autoplanner'. Locally I'd run python -m pytest, which adds the current folder to the import path; CI runs plain pytest. Fix: pythonpath = ["."] in pyproject.toml. I verified it the way CI runs: a fresh clone and a fresh virtual environment with only the requirements: 154 passed.

Others: Gemini's recommended model returned 503 on every image request, so it was switched through config; the keep-alive failed when a secret had a stray newline or quotes, so the secrets are cleaned first; the secret scan matched its own spec text.

9. Limitations and next steps

Limitations

  • No accounts: the link is the key, and the last write wins if two tabs edit.
  • The lower goals are near-optimal rather than proven. 30-task, 14-day weeks can take up to about 12 s.
  • Unconfirmed past blocks are assumed done (a deliberate decision, D-1).
  • The free tiers: Supabase pauses (hence the keep-alive), and Gemini's free tier may use the data it receives.
  • The calendar is cramped on phones (use the day view). IST only.
  • AC-17 (real-screenshot accuracy) and the AC-40 live security check are still to do.

Next

  • Run AC-17 and AC-40; rotate the API keys used during setup.
  • Optional login (Supabase Auth), with links kept for guests.
  • Solve in the background for big weeks; reuse the previous plan as a warm start.
  • Two-way Google Calendar sync instead of a one-way .ics file.
  • An automatic day view on phones; focus windows per weekday.

Product and users

1★ What problem does AutoPlanner solve, and for whom?

Students lose their plan as soon as one study session slips, and re-planning by hand is tedious. AutoPlanner plans the week automatically around classes and deadlines, and replans instantly when something doesn't happen. It's built for students like me whose assignments are in Microsoft Teams, and anyone can try a demo week without signing up.

2 How is it different from a to-do app or Google Calendar?

Those store what you schedule. AutoPlanner decides when to work: it places blocks so every deadline is met, puts demanding work in your focus hours, splits big tasks, and replans when something slips. When the work can't fit, it tells you by how much and offers checked fixes. It exports to Google Calendar, so it complements your calendar rather than replacing it.

3 Why screenshots instead of connecting to Teams directly?

I tested the Microsoft Graph route: IISc requires admin consent for the assignment permissions, so a student can't use it. A screenshot works for everyone. Windows+Shift+S, then Ctrl+V into the paste box, then Gemini reads it, and you review the rows before anything is saved.

Spec-driven development and requirements

4★ What is spec-driven development, and how did you apply it?

I wrote the specification before any code: SPEC.md has 68 EARS requirements and 48 pass/fail acceptance criteria, with Must/Should priorities. PLAN.md maps every task to its requirement and AC IDs, and its first phase was a live deployment check. Commits reference the IDs, and every change of direction became a logged spec change first. "Done" means the AC passes, not that it looks finished.

5 Why EARS format?

"WHEN trigger, THE SYSTEM SHALL response" forces every requirement to state when it applies and what observable behaviour is expected, which makes it testable. For example: "IF the hard model is proven infeasible, THEN THE SYSTEM SHALL show the banner with the exact shortfall and checked options" maps directly onto AC-10.

6 Give an example of a spec change during the build.

The benchmark's lateness check failed: 1281 h for the optimizer vs 1165 h for greedy. The cause was that the optimizer treated the min block length as a hard rule while the greedy baseline ignored it. Decision D-12 already said best-effort plans count short blocks rather than forbid them, so D-23 made the min block a soft goal in lateness mode. I logged it in v0.8 before changing the code, and the result became 782 h vs 1165 h. No AC target changed.

7 How do you know a requirement is done?

Each one has a pass/fail AC. Most are automated tests, and some are benchmark checks or live checks. PLAN.md's table records each AC's status and how it was verified. Where something hasn't been checked live, such as AC-17 or AC-40, it says so instead of claiming a pass.

Architecture and routing

8★ Walk me through the architecture.

It's a Streamlit app. streamlit_app.py routes on query parameters, and views in ui/ call a PlannerService. Every change goes through change → build the problem → solve with CP-SAT → diagnose if infeasible → validate independently → save. Storage is behind a repository interface: Supabase in production, in-memory for the demo and tests. Import is a separate pipeline (Gemini, Tesseract fallback, a local date resolver). GitHub Actions runs CI and a keep-alive.

9 How does routing work without login?

Query parameters. No parameters shows the landing page; ?demo=1 opens the demo with session-only data; ?p=<id> opens a planner. The ID is checked against a strict 43-character pattern and then looked up. Malformed and unknown IDs get the identical "Planner not found" message, and no planner is ever created from a URL.

10 What exactly happens when I click "Not done"?

The calendar click selects the block, once. The button calls run_action(service.mark_not_done). The service applies a pure state change, which returns the unfinished minutes to the task, then rebuilds the slot grid from now, solves, validates and saves. Past and done blocks stay frozen. The page reruns with a new calendar key, so the new plan shows immediately.

Features and code

11 How does screenshot import work?

The image goes inline to Gemini with a fixed JSON schema: title, course, due text and status. Gemini copies the due text exactly; it doesn't interpret dates. If there's no key, an error, a timeout, bad JSON or zero rows, Tesseract reads the image instead, after grayscale, inverting dark themes, upscaling 2× and stretching contrast, and a rule-based parser extracts the rows. Then a review table: duplicates, completed and past rows are unticked, and problem rows come first.

12 How do you turn "Due tomorrow at 11:59 PM" into a date?

Locally, in importers/dates.py, relative to the screenshot date, which the user can change. It handles today and tomorrow, weekday names (the next one strictly after; the same weekday means next week, flagged ambiguous), month and day with the closest year, ISO and numeric dates, 12- and 24-hour times, and 23:59 when no time is given. Every result carries a flag (inferred, ambiguous or unresolved) that shows in the review table. A table test has 31 cases.

13 How does the app learn from your actual time?

When you complete a task, I store the actual hours, but it only counts for learning if all of its blocks were confirmed: done or not done, not just assumed. For each type, factor = 1 + n/(n+2)·(r − 1), clamped to [0.5, 2.5], over the last 10 tasks. With three labs that took 1.5× their estimate, the factor is 1.3, so a new 2 h lab estimate is suggested as 2.5 h, which you can override.

14 How did you handle time zones?

Everything is IST (Asia/Kolkata, which has no DST) internally and UTC in the database. The calendar is given IST wall-clock times in UTC mode, so it shows IST in any browser. The .ics file uses TZID Asia/Kolkata with a VTIMEZONE block, and a test checks that 21:00 IST becomes 15:30 UTC.

Database and algorithms

15★ How does the scheduler work?

One Boolean per task and 30-minute slot. The hard constraints are:

  • only free slots, and at most one task per slot;
  • exactly the remaining work before each deadline;
  • a sliding window limits runs to the max block length;
  • start indicators force each block to the min length;
  • a daily cap, net of work already done today.

Then the goals are solved one at a time: demanding work in focus windows, fewer blocks, then earlier days. Each goal's value is fixed before the next starts, each has a time cap, and the solver starts from a complete hint plan.

16★ What happens when the deadlines can't all be met?

Strict mode is proven infeasible. A minimum-shortfall model then finds the exact hours H that can't fit, and gives a best-effort plan. For fixes, it cuts exactly that shortfall, and for up to 3 tasks it relaxes one deadline and minimises that task's finish time. Every option is re-solved before it's shown. Example: 11 h due today with an 8 h daily cap gives H = 3 h, and extending either task to Thursday 11:30 makes it fit.

17 Why solve the goals one after another instead of as a weighted sum?

I started with a weighted sum. Each goal alone proved optimal in about a second, but the combined objective couldn't be proven within 10 s, so the demo hit the limit. Solving lexicographically, with the best value fixed between goals, gives true priority order and lets me cap the lower goals' time. The demo median went from 10 s to about 0.85 s.

18 Describe the data model.

Five Postgres tables:

  • planners: a 43-character ID, plus prefs and plan metadata in jsonb;
  • events: one-off or weekly;
  • tasks: raw and used estimates, status, actual hours, learning eligibility;
  • blocks: planned, done, not done or skipped, with actual minutes and a plan version;
  • import_log: for the Gemini limit.

Row-level security is on with no anon policies; children are deleted with their planner.

19 How do you avoid re-solving on every Streamlit rerun?

Streamlit reruns the script on every interaction. I store a hash of everything that affects the plan (preferences, events, tasks, and blocks with feedback) next to the plan. Loading compares the hash and only re-solves if it changed (R62). A test counts solver calls to prove that two page loads don't re-solve.

Security and privacy

20★ There's no login. How is a planner private?

Each planner gets a 256-bit random ID from Python's secrets module (43 URL-safe characters), so it can't be guessed; the link works like a password, and the app warns you to bookmark it. The database is only reached from the server with the secret key. Row-level security blocks the public anon key, and every query is filtered by planner ID. The trade-off is that anyone holding the link can edit, which is accepted and documented (D-10).

21 How are secrets handled?

They live only in Streamlit secrets (the Cloud secrets box, or a git-ignored local file) and in GitHub encrypted secrets for the keep-alive. Code reads them through one accessor and never logs them. A log scrubber redacts key formats and planner IDs, a test scans every tracked file for real key formats, and the keep-alive masks its values and prints only the HTTP status.

22 What happens to the screenshots?

They're kept in memory only: sent inline to Gemini (not through the Files API), never written to disk, the database or logs, and the upload or paste widget is reset afterwards. A test checks that no image bytes or data URLs remain anywhere. The UI warns that screenshots go to Google Gemini; on the free tier Google may use them, so I suggest cropping to the assignment list.

Testing and CI

23★ How did you test it?

174 pytest tests, run offline: unit tests for the solver rules, validator, diagnosis, learning, date resolver and parsers; pipeline tests with a fake Gemini client; storage contract tests; and Streamlit AppTest tests for UI flows such as error handling, delete planner and overload. The benchmark is a test too: 90 workloads with pass/fail checks. CI runs everything on every push.

24 How do you test a Streamlit UI?

Streamlit's AppTest runs the real script headlessly: setting query parameters, clicking buttons, typing text and checking the output. For example, I stub the solver to raise an exception and assert that the page shows a plain message, no traceback, and unchanged data. Custom components (the calendar and paste box) can't be clicked in AppTest, so their logic is in pure functions that I test directly. The pages were also rendered in a headless browser at desktop and phone widths, and the clicks were checked live.

25 How do you test Gemini and Tesseract without the network?

Gemini is a fake client that records calls, so I can assert that the image went inline and the Files API wasn't used. Tesseract runs for real in CI on synthetic screenshots: generated from fictional data with hand-written labels, and marked so a real screenshot can never pass as a fixture. Locally, pytest-socket blocks every connection except localhost.

26 Tell me about a bug CI caught.

CI failed with "No module named autoplanner" before any test ran. I'd been running python -m pytest, which adds the current folder to the import path, while CI ran plain pytest. I reproduced it exactly in a fresh clone and virtual environment, fixed it with pytest's pythonpath setting, then re-verified the same way.

Scalability and failure scenarios

27 What if the solver runs out of time?

The solver has a 10 s limit. If it finds no plan and no proof of infeasibility, the app shows the greedy earliest-deadline-first plan with a banner and its counts of deadline misses and short blocks. Every plan, including the fallback, passes the independent validator before it's saved; if the validator ever failed, the previous plan would be kept.

28 What if Supabase is down or paused?

Storage errors become a plain "Storage is unavailable" message, and nothing is half-saved. Writes go new rows first and the plan metadata last, so a failure leaves a stale hash and the next load replans. The demo doesn't use Supabase at all, so it keeps working. A keep-alive job every third day stops the free project pausing.

29 How would this scale to many users?

Each solve is independent and small (a week of 30-minute slots), so it scales horizontally. The bottleneck is CPU on the free container: 30-task, 14-day weeks take up to about 12 s. Next steps would be solving in a background worker, reusing the previous plan as a warm start, a paid tier or a separate solver service, and connection pooling for Postgres.

Deployment and cost

30 How is it deployed, and what does it cost?

Nothing: it uses free tiers only (SPEC constraint C1). Streamlit Community Cloud deploys from main on Python 3.13, with Tesseract installed through packages.txt. Supabase's free Postgres, Gemini's free tier and GitHub Actions cover the rest. Phase 1 of the plan was deploying a smoke page that proved Supabase and Gemini worked on Cloud before any feature code.

31 Why a keep-alive workflow?

Free Supabase projects pause after about a week without activity, which would break every planner link. A GitHub Action reads one row every third day. It cleans the secrets first (a stray newline or quotes in a secret once caused "Malformed input to a URL function"), and fails clearly without printing values. One caveat: GitHub disables scheduled workflows in public repos after 60 days without activity, and the README explains how to re-enable it.

Trade-offs: "why not X?"

35★ Why not just use a greedy algorithm?

I measured it. On 90 seeded workloads against greedy earliest-deadline-first, the optimizer met more deadlines (1725 vs 1674), had less total lateness (782 h vs 1165 h) and far fewer preference violations (3089 vs 4479). When everything fits, both meet every deadline, but the optimizer puts demanding work in focus hours (62–95 % fewer violations). The cost is solve time: a median of 1.5 s for 20 tasks, against near zero for greedy. Greedy remains the fallback.

36 Why Streamlit rather than a React front end with an API?

The budget was 3 days and free hosting. Streamlit gave me one language, free deployment and built-in widgets, so the time went into the scheduling and import logic. The costs are less control over the UI and a rerun-based model, which I handled with the input hash and custom components where needed (the calendar and paste box). For a larger product, I'd split out a FastAPI backend.

37 Why Supabase rather than SQLite?

Streamlit Cloud's file system is temporary, so SQLite data would be lost on restart. Supabase gives real Postgres for free, with row-level security and a REST client. The repository interface means the app doesn't depend on it: tests and the demo run on an in-memory store.

Future work

38★ What's the biggest limitation, and what would you build next?

The biggest limitations are trust and reach: no accounts (the link is the key), and real-screenshot accuracy hasn't been measured yet (AC-17). Next I'd run AC-17 and the live security check, add optional Supabase Auth, move solving to a background worker for big weeks, add two-way Google Calendar sync, and switch phones to the day view automatically.
